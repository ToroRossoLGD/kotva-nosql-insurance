KOTVA - NOSQL INFORMACIONI SISTEM ZA OSIGURAVAJUĆE DRUŠTVO
============================================================

Verzija dokumentacije: 31. avgust 2026.
Naziv projekta: Kotva
Tip projekta: NoSQL web aplikacija
Baza podataka: ArangoDB 3.12
Backend: Node.js i Express
Frontend: HTML, CSS, JavaScript i Chart.js


1. OPIS PROJEKTA
-----------------

Kotva je informacioni sistem za evidentiranje osiguranika, polisa i
osiguravajućih kuća. Sistem omogućava unos novih korisnika i osiguravajućih
kuća, čuvanje podataka u ArangoDB bazi, pretragu korisnika i prikaz poslovne
analitike pomoću grafikona.

Podržane vrste osiguranja su:

- Putno osiguranje
- Životno osiguranje
- Auto-osiguranje
- Osiguranje privatne svojine

Početne osiguravajuće kuće su:

- Uniqa
- Generali
- Milenijum
- Sava

Sistem je proširiv, pa se nove kuće i novi korisnici mogu unositi preko
frontenda. Grafikoni se automatski osvežavaju nakon unosa.


2. GLAVNE FUNKCIONALNOSTI
-------------------------

- Unos imena i prezimena korisnika
- Unos godina korisnika
- Izbor vrste osiguranja
- Izbor osiguravajuće kuće
- Unos datuma prodaje polise
- Dodavanje novih osiguravajućih kuća
- Prikaz poslednjih korisnika
- Pretraga korisnika po imenu ili prezimenu
- Pretraga bez obzira na velika slova i dijakritike
- Automatsko kreiranje polise i graph veza za novog korisnika
- Analitika i interaktivni grafikoni
- ArangoDB web interfejs
- Trajno čuvanje podataka u Docker volumenu
- Rezervni režim rada u memoriji kada ArangoDB nije dostupan

6. NOSQL I ARANGODB
-------------------

NoSQL označava baze koje nisu ograničene isključivo na relacioni model tabela.
ArangoDB je multi-model NoSQL baza koja podržava:

- document model
- key-value pristup
- graph model
- full-text pretragu
- AQL upite

Dokumenti su JSON-slične strukture. ArangoDB je schema-free, što znači da svi
dokumenti ne moraju imati potpuno identična polja. Ipak, aplikacija koristi
backend validaciju kako bi održala kvalitet podataka.


7. KOLEKCIJE
------------

Document kolekcije:

1. clients
   Čuva korisnike i osnovne informacije o njihovom osiguranju.

2. insurers
   Čuva osiguravajuće kuće.

3. policies
   Čuva zasebne dokumente polisa.

Edge kolekcije:

4. owns
   Povezuje korisnika sa polisom.

5. issued_by
   Povezuje polisu sa osiguravajućom kućom.


8. PRIMER DOKUMENTA KORISNIKA
-----------------------------

{
  "_key": "korisnik-1",
  "_id": "clients/korisnik-1",
  "_rev": "revizija-dokumenta",
  "id": "korisnik-1",
  "name": "Ana",
  "surname": "Marković",
  "age": 29,
  "insuranceType": "Putno",
  "insurer": "Uniqa",
  "saleDate": "2026-01-15"
}

Sistemska polja:

- _key: jedinstveni ključ dokumenta unutar kolekcije
- _id: naziv kolekcije i ključ dokumenta
- _rev: identifikator trenutne revizije dokumenta

Polje _rev se menja prilikom izmene dokumenta i može se koristiti za optimistic
concurrency control, odnosno sprečavanje prepisivanja tuđih izmena.


9. PRIMER DOKUMENTA POLISE
--------------------------

{
  "_key": "polisa-korisnik-1",
  "clientId": "korisnik-1",
  "insuranceType": "Putno",
  "saleDate": "2026-01-15",
  "validFrom": "2026-01-15",
  "validUntil": "2027-01-15",
  "premium": 4225,
  "status": "Aktivna"
}

Premija se trenutno izračunava demonstracionom formulom na osnovu vrste
osiguranja i godina korisnika.


10. GRAPH MODEL
---------------

Naziv grafa:

kotva_insurance_graph

Struktura:

clients --owns--> policies --issued_by--> insurers

Primer owns veze:

{
  "_from": "clients/korisnik-1",
  "_to": "policies/polisa-korisnik-1"
}

Primer issued_by veze:

{
  "_from": "policies/polisa-korisnik-1",
  "_to": "insurers/kuca-1"
}

Graph model omogućava da jedan korisnik u budućnosti ima više polisa i da se
efikasno pronalaze sve polise određene kuće ili korisnika.


11. GRAPH TRAVERSAL
-------------------

Graph traversal je obilazak povezanih čvorova praćenjem edge veza.

Smerovi:

- OUTBOUND prati smer _from -> _to
- INBOUND prati smer _to -> _from
- ANY ignoriše smer veze

Primer pronalaženja polisa korisnika:

FOR policy IN 1..1 OUTBOUND "clients/korisnik-1" owns
  RETURN policy

Brojevi 1..1 znače da se obilazi tačno jedna veza u dubinu.

Primer obilaska named grafa do dubine dva:

FOR vertex, edge, path
  IN 1..2 OUTBOUND "clients/korisnik-1"
  GRAPH "kotva_insurance_graph"
  RETURN {
    vertex: vertex,
    edge: edge,
    path: path
  }


12. ANALYZER I PRETRAGA
-----------------------

Analyzer:

kotva::sr_name_search

Tip:

norm

Podešavanja:

- locale: sr
- case: lower
- accent: false

Analyzer normalizuje tekst, tako da pretraga "Markovic" može pronaći
"Marković". Koristi se zajedno sa inverted indeksom i SearchAlias view-om.

Inverted indeks:

idx_client_name_search

Indeksirana polja:

- name
- surname

Search view:

client_search

Frontend koristi API rutu:

GET /api/search?q=Markovic


13. INDEKSI
-----------

Primary indeks:

- automatski postoji
- indeksira _key
- jedinstven je

Persistent indeks:

idx_insurance_type_sale_date

Polja redom:

1. insuranceType
2. saleDate

Indeks je pogodan za upite koji koriste jednakost nad insuranceType i opseg ili
sortiranje nad saleDate.

Primer:

FOR client IN clients
  FILTER client.insuranceType == "Putno"
  FILTER client.saleDate >= "2026-07-01"
  FILTER client.saleDate < "2026-08-01"
  SORT client.saleDate
  RETURN {
    korisnik: CONCAT(client.name, " ", client.surname),
    datumProdaje: client.saleDate,
    osiguravajucaKuca: client.insurer
  }

U Explain planu treba da se pojavi IndexNode i naziv indeksa
idx_insurance_type_sale_date.

Indeksi ubrzavaju čitanje, ali zauzimaju dodatni prostor i usporavaju upis jer
se moraju ažurirati nakon svake promene dokumenta.

17. PRIMERI AQL UPITA
---------------------

17.1. Svi korisnici

FOR client IN clients
  SORT client.surname, client.name
  RETURN client

17.2. Korisnici auto-osiguranja

FOR client IN clients
  FILTER client.insuranceType == "Auto"
  SORT client.age DESC
  RETURN {
    ime: client.name,
    prezime: client.surname,
    godine: client.age,
    osiguravajucaKuca: client.insurer
  }

17.3. Broj korisnika po kući

FOR client IN clients
  COLLECT insurer = client.insurer WITH COUNT INTO total
  SORT total DESC
  RETURN {
    osiguravajucaKuca: insurer,
    brojOsiguranika: total
  }

17.4. Procenat zastupljenosti kuća

LET totalClients = LENGTH(clients)

FOR client IN clients
  COLLECT insurer = client.insurer WITH COUNT INTO clientCount
  LET percentage = ROUND(clientCount * 10000 / totalClients) / 100
  SORT clientCount DESC
  RETURN {
    osiguravajucaKuca: insurer,
    brojOsiguranika: clientCount,
    procenat: percentage
  }

17.5. Prosečne godine po vrsti osiguranja

FOR client IN clients
  COLLECT type = client.insuranceType
  AGGREGATE averageAge = AVERAGE(client.age)
  SORT averageAge DESC
  RETURN {
    tipOsiguranja: type,
    prosecneGodine: ROUND(averageAge * 10) / 10
  }

17.6. Putne polise tokom jula

FOR client IN clients
  FILTER client.insuranceType == "Putno"
  FILTER DATE_MONTH(client.saleDate) == 7
  COLLECT day = DATE_DAY(client.saleDate) WITH COUNT INTO policies
  SORT day
  RETURN {
    dan: day,
    brojPolisa: policies
  }

17.7. Najprodavanija vrsta osiguranja

FOR client IN clients
  COLLECT type = client.insuranceType WITH COUNT INTO total
  SORT total DESC
  LIMIT 1
  RETURN {
    tip: type,
    brojPolisa: total
  }

17.8. Polise jednog korisnika preko grafa

FOR policy IN 1..1 OUTBOUND "clients/korisnik-1" owns
  RETURN policy


18. VREMENSKA I MEMORIJSKA KOMPLEKSNOST
----------------------------------------

Oznake:

- N: broj korisnika
- P: broj polisa
- I: broj osiguravajućih kuća
- V: broj graph čvorova
- E: broj graph veza
- R: broj rezultata upita

Pronalaženje bez indeksa:

O(N)

Indeksirano pronalaženje:

Približno O(log N + R)

Sortiranje bez odgovarajućeg indeksa:

O(N log N) vreme i do O(N) dodatna memorija

Agregacija po osiguravajućoj kući:

O(N + I log I) vreme i O(I) memorija

Prosek starosti:

O(N) vreme

Mesečna analitika:

O(P) vreme i O(1) dodatna memorija, jer postoji 12 meseci

Julska dnevna analitika:

O(P) vreme i O(1) memorija, jer postoje najviše 31 brojač

Graph traversal u najgorem slučaju:

O(V + E)

Traversal ograničen na dubinu jedan ili dva obično obilazi samo relevantan deo
grafa. Edge indeksi nad _from i _to ubrzavaju pronalaženje susednih čvorova.

Prostor graph modela:

O(N + P + E)

Pošto svaki korisnik trenutno ima jednu polisu i dve veze, ukupna prostorna
složenost ostaje linearna O(N), ali uz veći konstantni faktor.

Inverted indeks:

- kreiranje: približno O(N * L), gde je L količina teksta
- pretraga: približno O(log T + R), gde je T broj termina
- memorija: proporcionalna terminima i referencama ka dokumentima

   Dodavati ih samo za često korišćene FILTER i SORT operacije.


20. SKALIRANJE SISTEMA
----------------------

Prvi nivo skaliranja:

- optimizacija AQL upita
- indeksi
- paginacija
- keširanje
- preagregirana statistika
- slanje samo potrebnih polja

Horizontalno skaliranje:

- ArangoDB klaster
- sharding kolekcija
- replikacija shardova
- više backend instanci
- load balancer
- zajednički distribuirani keš

Sharding deli različite delove podataka između servera. Replikacija čuva kopije
istih podataka radi dostupnosti i oporavka.

Backend treba da bude stateless, odnosno trajno stanje ne treba čuvati u
memoriji jedne Node instance.


21. CAP, ACID I BASE
--------------------

CAP teorema govori o kompromisu distribuiranih sistema između:

- Consistency
- Availability
- Partition tolerance

Trenutni projekat koristi single-server ArangoDB, pa CAP kompromis nije
praktično demonstriran. Postao bi važan u klasteru.

ACID:

- Atomicity: sve operacije uspevaju ili se sve poništavaju
- Consistency: podaci ostaju validni
- Isolation: paralelne transakcije se ne ometaju neispravno
- Durability: potvrđeni podaci ostaju trajno sačuvani

BASE se često koristi za opis distribuiranih sistema sa eventual consistency
modelom:

- Basically Available
- Soft state
- Eventual consistency


22. NORMALIZACIJA I DENORMALIZACIJA
-----------------------------------

Denormalizacija znači namerno ponavljanje podataka radi jednostavnijeg i bržeg
čitanja. U client dokumentu postoji naziv insurer iako postoji insurers
kolekcija.

Prednosti:

- jednostavniji upiti
- brža analitika

Mane:

- promena naziva može zahtevati izmenu više dokumenata
- mogućnost nekonzistentnosti

Graph model client -> policy -> insurer predstavlja strukturisaniji model veza
i omogućava više polisa po korisniku.

25. MOGUĆA PITANJA PROFESORA
----------------------------

Pitanje: Zašto ArangoDB?
Odgovor: Zato što je multi-model baza koja u jednom sistemu podržava dokumente,
grafove, AQL, indekse i pretragu. Projekat koristi i document i graph model.

Pitanje: Zašto NoSQL umesto relacione baze?
Odgovor: Različite vrste polisa mogu imati različita dodatna polja, a document
model omogućava fleksibilno proširenje bez promene rigidne šeme svih zapisa.

Pitanje: Šta je graph traversal?
Odgovor: Obilazak povezanih čvorova praćenjem edge veza u OUTBOUND, INBOUND ili
ANY smeru do određene dubine.

Pitanje: Šta je _rev?
Odgovor: Identifikator trenutne revizije dokumenta koji se može koristiti za
otkrivanje konflikata pri paralelnim izmenama.

Pitanje: Čemu služi indeks?
Odgovor: Ubrzava filtriranje i sortiranje, ali zauzima dodatni prostor i
usporava upis jer se mora održavati.

Pitanje: Šta je selectivity?
Odgovor: Procena koliko dobro indeks razlikuje dokumente. Više različitih
vrednosti uglavnom znači veću selektivnost.

Pitanje: Šta je analyzer?
Odgovor: Komponenta koja normalizuje ili tokenizuje tekst pre indeksiranja i
pretrage. U projektu omogućava da Markovic pronađe Marković.

Pitanje: Kako sprečavaš neispravne podatke?
Odgovor: Backend proverava obavezna polja, godine, datum, tip osiguranja i
postojanje kuće. Moguća je i JSON Schema validacija u ArangoDB-u.

Pitanje: Kako sprečavaš duplikate?
Odgovor: Dokument ima jedinstveni _key, a backend proverava naziv kuće bez
obzira na velika slova.

Pitanje: Kako bi sistem skalirao?
Odgovor: Najpre indeksima, AQL agregacijama, paginacijom, keširanjem i
preagregiranim statistikama, a zatim ArangoDB klasterom, shardingom,
replikacijom i više stateless backend instanci iza load balancera.

Pitanje: Koje je ograničenje trenutne verzije?
Odgovor: Sistem je demonstraciona single-server implementacija. Produkcijska
verzija bi koristila transakcije, selektivnu graph sinhronizaciju, paginaciju,
autorizaciju, backup i klaster za veliki obim podataka.

28. ZAKLJUČAK
-------------

Kotva demonstrira praktičnu upotrebu ArangoDB multi-model baze. Sistem koristi
dokumente za korisnike, polise i kuće, edge dokumente za odnose, named graph za
vizuelizaciju, analyzer i inverted indeks za pretragu, persistent indeks za
filtriranje po vrsti i datumu, kao i AQL za analitiku.

Projekat pokazuje glavne NoSQL koncepte: fleksibilan dokument model,
denormalizaciju, indeksiranje, graph traversal, agregaciju, horizontalno
skaliranje, sharding, replikaciju i kompromis između brzine čitanja, brzine
upisa i zauzeća memorije.
